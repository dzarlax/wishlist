Implementation Plan: Wishlist List Homepage Refresh

Branch: codex/homepage-refresh-plan. Created after PR #2 was merged and deployed.

Task Summary

Plan a focused refresh of the root homepage: available wishlists first, then a fuller explanation section that describes how to use this hosted wishlist service and why it is useful. The target is only the no-slug homepage rendered before a specific wishlist is opened. The selected wishlist screen, filters, gift grid, and gift cards are intentionally out of scope.

Current Behavior

  • frontend/src/App.svelte owns routing, auth state, selected wishlist, filters, sorting, modals, and the gift grid.
  • The root route with multiple users renders UserSelect.svelte: a centered title, subtitle, and user cards.
  • A selected wishlist route #/<slug> renders the current wishlist browsing screen; this plan should not change that screen.
  • If exactly one user exists, the app automatically navigates to that user.
  • Invite registration is a hash route at #/invite/<token> and should stay functionally separate.
  • Auth is now JWT-based; gift creation/editing is owner-only, AI controls depend on can_use_ai, and admin controls live in settings.

Desired Behavior

  • Make the first viewport feel like a polished wishlist directory, not just a centered picker.
  • Keep available wishlists as the primary signal: names, avatars, slugs, and clear open actions.
  • Preserve simple navigation: selecting a user should still route to #/<slug>.
  • Add a fuller explanation area below the directory: what guests can do, what wishlist owners can do, how reservations work, and why secret codes matter.
  • Frame this as the hosted service managed by the site admin, not as a self-hosted product or installable app.
  • Be clear that new wishlist owners are added by invite/admin approval; public users do not self-administer the service.
  • Make the page visually polished: intentional spacing, restrained palette, clean hierarchy, and no cramped or placeholder-looking blocks.
  • Design mobile as a first-class view: wishlist cards first, explanation sections stacked cleanly, no clipped buttons or overlapping text.
  • Respect existing design constraints: no marketing landing page, no decorative gradient/orb backgrounds, no nested cards, no remote assets.
  • Keep all copy localized in Russian, English, and Serbian.

Proposed UX Direction

  • Replace the simple centered picker with a full-width app home section and a denser wishlist directory.
  • Show concise product identity: Wishlist, available lists, and a direct "open wishlist" affordance per user.
  • Make each user card easier to scan with avatar, name, slug, and optionally lightweight counts if they are already available without extra API work.
  • Add usage-focused sections below the directory: how to reserve, how to manage your own wishlist after login, what AI autofill does, and how anonymity works.
  • Keep the directory above the explanatory content so repeat visitors can open a wishlist without scrolling through copy.
  • Avoid self-hosting language, pricing language, public signup promises, or admin-facing claims. Admin is the site owner only.
  • Use a polished but practical visual treatment: wide bands, balanced whitespace, clear cards for individual wishlists/features, and crisp mobile stacking.
  • Keep the no-user state practical and configuration-focused.
  • Do not change the selected wishlist header, filters, gift cards, archive, reservation flow, or owner controls in this iteration.

Assumptions and Unknowns

  • Assumption: "главная страница" now means only the root user selection / wishlist directory page.
  • Assumption: no new backend data is required; user cards should use the existing /api/users response.
  • Assumption: the current ivory/dark editorial visual language should remain, but with less sparse composition.
  • Decision: include a fuller explanatory area below the directory to explain this hosted service for normal users.
  • Decision: do not describe the product as self-hosted, installable, or publicly administered by users.
  • Decision: admin capability belongs to the site owner; new owners join through invite/approval.
  • Decision: phrase invite/approval softly on the homepage: users can contact the administrator if they want their own wishlist.
  • Unknown: whether the root home should show only user cards or lightweight public counts; counts would require either API changes or extra gift fetches.
  • Decision for this scope: owner-only admin actions stay inside selected wishlist/settings, not on the root directory.

Files Likely to Change

  • frontend/src/lib/UserSelect.svelte - refresh root home/user selection screen.
  • frontend/src/App.svelte - likely only minor container/header adjustments around the no-current-user branch, if needed.
  • frontend/src/lib/locales/ru.json, en.json, sr.json - add localized labels for root homepage and usage explanation copy.
  • frontend/tests/App.test.js - update expectations for new root home copy and user selection behavior.
  • Optional: frontend/src/lib/components/ - introduce small presentational components only if UserSelect.svelte becomes too large.
  • Optional: frontend/src/app.css or design token utilities - only for reusable layout tokens; avoid one-off global CSS.

Implementation Steps

  1. Refresh UserSelect.svelte with a more useful root home layout while keeping direct user selection as the primary action.
  2. Keep the current header controls visible and avoid duplicating login/settings behavior on the root page.
  3. Add below-directory explanation sections for gift giver flow, wishlist owner flow, AI autofill, invite/approval, and privacy/secret-code rules.
  4. Update no-user state so it can still explain the service without exposing operational details to normal users.
  5. Add locale keys in all supported languages and avoid hardcoded visible copy in Svelte components.
  6. Implement responsive layout deliberately: desktop directory grid, tablet wrapping, single-column mobile flow, and touch-friendly buttons.
  7. Update tests for user-selection and invite route non-regression.
  8. Run browser QA at desktop and mobile widths before completing implementation.

Impact

  • Data/API: no backend endpoint or schema change expected.
  • Auth/permissions: no permission contract change; UI copy should make existing owner-only behavior clearer.
  • Deployment: normal frontend build and Docker image pipeline only.
  • UX: visible layout and copy changes only on the root homepage: wishlist directory first, usage explanation below.
  • Localization: all new visible strings must be added to Russian, English, and Serbian locale files.
  • Accessibility: preserve keyboard navigation, semantic buttons, visible focus, and responsive text fitting.
  • Mobile: mobile view is part of the implementation scope, not a follow-up.

Test Plan

  • npm run lint
  • npm test
  • npm test -- --run from frontend/
  • npm run build
  • Browser QA with the in-app browser against a local dev server or built app preview.
  • Visual QA screenshots/checks at desktop and mobile widths, including 390px mobile viewport.

Manual QA Checklist

  • Root route with multiple users shows the refreshed wishlist directory and each user is selectable.
  • Explanation sections appear below the directory and do not push wishlist cards out of the first viewport on common desktop sizes.
  • Single-user auto-navigation still works.
  • #/alexey or another user slug still shows the existing wishlist view unchanged.
  • Invite route #/invite/<token> still shows registration and is not affected by homepage layout.
  • Mobile layout keeps wishlist cards first and stacks explanation sections without overlap.
  • All new homepage copy appears correctly in Russian, English, and Serbian after switching languages.
  • Buttons and card labels fit on narrow mobile screens without clipping or awkward wrapping.
  • Dark and light themes remain legible.

Risks and Edge Cases

  • Root homepage can start feeling like marketing if explanation copy becomes promotional; keep it instructional and concrete.
  • Copy must not imply open public signup, self-hosting, or user-administered access.
  • Fuller explanation copy increases localization scope; keep section copy concise and concrete.
  • A visually richer homepage can become too decorative; keep the design elegant but functional, with the wishlist directory as the first actionable area.
  • Extra public counts can create API/performance creep; avoid counts unless they come from existing data cheaply.
  • Root route behavior differs for one user vs multiple users; both paths need explicit testing.
  • Copy additions must be added to all three locale files to avoid fallback gaps.

Rollback Plan

Revert the homepage refresh commit. Since the plan does not require backend, schema, or API changes, rollback should restore the previous frontend layout without data migration work.

Open Questions

  • Should the root home show only user cards, or also public counts per wishlist?
  • How deep should the usage explanation go in v1: explanation cards only, or also a short FAQ?
  • Resolved: use a soft invite/admin line rather than a hard restriction message.
  • Should there be a search/filter for users if the list grows, or is the current user count small enough to avoid it?
