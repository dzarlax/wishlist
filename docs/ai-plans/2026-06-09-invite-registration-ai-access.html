Invite Registration And AI Access Plan

Created: 2026-06-09. Repository: D:\Projects\Code\Personal\wishlist.

Task Summary

Add invite-link registration with admin approval-by-invite and separate AI access control. The feature must stay compatible with the current multi-user wishlist model, password login, optional Authentik SSO, SQLite fallback, and PostgreSQL deployment.

Current Behavior

  • Users are provisioned from the USERS environment variable on startup.
  • Existing users are updated by slug for name, emoji, and email; passwords are not overwritten after creation.
  • Password login uses POST /api/auth/login and returns a JWT.
  • SSO is optional and maps Authentik email to users.email.
  • Wishlist owner operations use requireOwner; guests can view wishlists and reserve gifts with a secret code.
  • POST /api/parse-gift is currently public. POST /api/translate is authenticated.
  • Production deploy lives in personal_ai_stack/deploy/wishlist and uses PostgreSQL schema wishlist.

Desired Behavior

  • Only system admins can create invite links.
  • Invite links are one-time-use and expire after 7 days.
  • Invite creation includes an AI access flag.
  • Accepting an invite creates a normal non-admin user with can_use_ai copied from the invite.
  • Admins can later toggle can_use_ai and is_admin for users.
  • Existing users keep working without manual migration steps.
  • AI endpoints require login and explicit AI access.

Confirmed Decisions

  • Use built-in invite registration, not public self-registration and not Authentik-only provisioning.
  • Add a global is_admin user flag. Initial admin is alexey.
  • Add a separate can_use_ai user flag.
  • Existing users receive can_use_ai=true for compatibility.
  • Invite links are single-use and expire after 7 days.
  • Guests still cannot create gifts. AI access is only relevant inside authenticated owner workflows.

Assumptions

  • The first production admin should be the existing user with slug alexey.
  • Invite email is optional. If present, it becomes the user's email and enables later SSO mapping.
  • New invite registrations should require stronger passwords than the current legacy minimum of 3 characters.
  • The implementation should not remove the USERS fallback in this change.
  • No email delivery is required. Admin copies and sends the generated invite URL manually.

Data Model

Add fields to users:

  • is_admin BOOLEAN NOT NULL DEFAULT false
  • can_use_ai BOOLEAN NOT NULL DEFAULT false

Add invites table:

id

used_by_user_id

Store a hash of the invite token, not the raw token. The URL contains the raw random token, and the backend hashes it for lookup.

API Changes

Admin-only endpoints:

  • GET /api/admin/invites - list active, used, expired, and revoked invites.
  • POST /api/admin/invites - create an invite and return the invite URL.
  • POST /api/admin/invites/:id/revoke - revoke an unused invite.
  • GET /api/admin/users - list users with access flags.
  • PATCH /api/admin/users/:id/access - update is_admin and can_use_ai.

Public invite endpoints:

  • GET /api/invites/:token - validate an invite and return safe display data.
  • POST /api/invites/:token/accept - create the user, mark the invite used, and return JWT plus user.

Access middleware:

  • Add requireAdmin for admin endpoints.
  • Add requireAiAccess for AI endpoints.
  • Change POST /api/parse-gift to require auth and AI access.
  • Change POST /api/translate to require AI access in addition to auth.

Frontend Changes

  • Add hash route handling for #/invite/<token>.
  • Add invite registration view with name, slug, password, and confirm password.
  • After invite acceptance, store JWT and navigate to the new user's wishlist.
  • Add admin section in settings when authUser.is_admin=true.
  • Admin section includes invite creation, invite listing/revocation, and user access toggles.
  • Show AI autofill UI only when isOwner && authUser.can_use_ai.
  • Manual gift creation remains available for owners without AI access.

Manual QA Checklist

  • Admin logs in and sees the admin section.
  • Admin creates an invite with AI access disabled and copies the URL.
  • Invite URL opens registration form and pre-fills available hints.
  • Accepting invite logs in the new user and opens their wishlist.
  • Used invite cannot be accepted again.
  • Revoked invite cannot be accepted.
  • Owner without AI access can manually create a gift but does not see AI autofill.
  • Admin toggles AI access and the user sees AI UI after reloading auth state.
  • Existing users can still log in and manage their existing wishlists.
  • SSO still works for users with matching email.

Risks

  • Migration SQL must handle SQLite and PostgreSQL differences for booleans and timestamps.
  • Existing documentation still describes the old single-admin password model and may need follow-up cleanup.
  • Changing /api/parse-gift from public to authenticated can break any external caller, if one exists.
  • Admin UI in the current settings modal could become crowded; keep the first pass minimal.
  • Invite token handling must avoid logging raw tokens in server logs.

Rollback Plan

  • Frontend changes can be reverted without data loss; existing users and gifts remain.
  • If invite endpoints fail, disable invite UI and continue provisioning via USERS temporarily.
  • Do not remove existing login or USERS seeding in this change, so rollback does not require recreating users.
  • Database columns and invite table can remain unused if the feature is disabled.

Resolved Questions

  • Email is optional. Invite creation must not require it.
  • Invite creation cannot grant admin rights. Admin rights are assigned only after registration through user access management.
  • Invite URLs should use hash routing: https://wishlist.dzarlax.dev/#/invite/<token>. This is the best fit for the current SPA and deploy setup because it does not require additional backend path handling or Traefik rewrite rules.

Known Limitations

  • No email delivery is implemented; admins copy invite links manually.
  • Invite acceptance is not wrapped in a database transaction because the current DB adapter does not expose transaction helpers.
  • Clean path routing such as /invite/:token was intentionally not added; hash routing remains the compatibility path.
  • Build and tests no longer emit Svelte component warnings; only the external Browserslist data age notice remains.
