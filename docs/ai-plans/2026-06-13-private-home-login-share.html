Private Root Homepage, Owner Login, and Copyable Wishlist Links

Plan the next iteration of the Wishlist app so the root homepage no longer exposes the list of all wishlists, wishlist owners can log in from the homepage, guests continue to open lists by direct link, and each opened wishlist has an easy share-link action.

Task Summary

Replace the root # experience from a public wishlist directory into a simple entry screen: explain that guests use direct links, provide a login button for wishlist owners, and avoid showing all available users on the main page.

Add a copy-link affordance on an opened wishlist route such as #/alexey, so the owner or a guest can quickly copy the direct URL and send it elsewhere.

Current Behavior From Code Inspection

  • frontend/src/App.svelte owns hash routing, auth state, selected user state, modals, filters, and gift grid rendering.
  • The root route currently renders UserSelect.svelte, which displays all users returned by GET /api/users.
  • Direct wishlist links already exist as hash routes: #/<slug>.
  • Owner login already exists through LoginModal.svelte, but it currently requires a known userSlug and is only shown after a wishlist is opened.
  • JWT auth is stored in frontend/src/lib/stores/auth.js and POST /api/auth/login accepts { slug, password }.
  • GET /api/users/:slug exists on the backend, while GET /api/users exposes the whole sanitized user list.
  • Locale files already contain root-homepage and auth copy in Russian, English, and Serbian.

Desired Behavior

Root homepage No public list of wishlist owners. Show concise app identity, a primary owner login button, and short guest guidance: "open the link you received."
Owner login From the root page, the owner can enter their username and password. After successful login, navigate to #/<slug>.
Guest access Guests open a direct URL such as https://host/#/alexey; they can browse and reserve gifts without seeing a directory of other wishlists.

Primary Implementation Approach

Recommended: frontend-only behavior change first.

  • Keep /api/users for now because App.svelte relies on it to resolve hash slugs and handle the single-user redirect path.
  • Replace the visual root directory with a new root entry component or repurpose UserSelect.svelte into a non-directory home screen.
  • Keep login fields inside LoginModal.svelte; the root page should expose only a login button/CTA, not a persistent login form.
  • Extend LoginModal.svelte so it can optionally collect a username when no userSlug is provided.
  • On successful root login, use the returned user from auth.loginWithPassword(slug, password) to navigate to #/<slug>.
  • Add a share/copy button in the selected wishlist header that copies window.location.origin + window.location.pathname + '#/' + currentUser.slug.
  • Use navigator.clipboard.writeText with a fallback for older or restricted browser contexts.

Privacy Boundary

This plan removes the public list from the homepage UI. It does not make wishlist slugs secret at the API level, because GET /api/users would still expose sanitized users.

If the requirement is "do not expose the list of users through the API either," that becomes a backend/API-contract change: replace root directory usage with direct /api/users/:slug lookup, adjust tests, and restrict or remove public /api/users. That is possible, but it has more compatibility risk and should be approved explicitly.

Likely File Changes

  • frontend/src/App.svelte - root route rendering, root login trigger, post-login navigation, copy-link handler, selected wishlist header controls.
  • frontend/src/lib/UserSelect.svelte - either replace with a non-directory homepage or split into a new component such as HomeEntry.svelte.
  • frontend/src/lib/LoginModal.svelte - support root login by adding a wishlist-address/slug field when userSlug is absent.
  • frontend/src/lib/locales/ru.json, en.json, sr.json - add copy for root login, direct-link guidance, slug field, and share-link success/error labels.
  • frontend/tests/App.test.js - update root homepage tests, add owner-login/root behavior expectations if practical, and add share-link rendering checks.
  • Optional backend follow-up only if API privacy is required: server.js, frontend/src/lib/utils/api.js, and tests around user lookup.

Implementation Steps After Approval

  1. Introduce a root home state that does not render any user cards or user names.
  2. Add a root-visible login button. When clicked, open the existing login modal in "username + password" mode.
  3. Normalize the entered username on the client: trim whitespace, remove a leading @, and lower-case it.
  4. After successful password login, navigate to the returned user's direct wishlist route.
  5. Add a share button on selected wishlist pages near the title/header actions, visible to guests and owners.
  6. Use localized toast messages for copied link and copy failure.
  7. Update tests and run the frontend test/build checks.
  8. Update this HTML plan with actual changed files, checks run, known limitations, and follow-up recommendations.

UI Direction

  • Stay inside the existing Svelte/Tailwind visual language: ivory/dark backgrounds, 8px panels where needed, compact utility buttons, and existing header controls.
  • Do not create a public marketing landing page. The first screen should be a functional entry screen.
  • Main root action: Войти for owners. The page should not show a permanent login form; fields belong in the modal.
  • Wishlist page share action should be low-friction and not compete with owner-only add/settings buttons.
  • On mobile, header controls must wrap cleanly without hiding login/share actions.

Assumptions

  • "Убрать список виш-листов" means remove the public visual directory from the root homepage.
  • Direct links can continue using the existing #/<slug> format.
  • Owners know their username. Direct wishlist links are for guests, not for owner login.
  • Guest reservation flow stays unchanged: no login required, secret code required for reservation management.
  • No database schema or migration is needed for the frontend-only version.

Test Plan

  • Run root app tests with npm test or the project-specific frontend Vitest command after implementation.
  • Run production build with npm run build.
  • Verify locale JSON remains valid and all new keys exist in ru, en, and sr.
  • Browser QA root route: no user cards or names visible; owner login opens from the main page.
  • Browser QA direct route: #/<slug> still loads that wishlist for guests.
  • Browser QA owner route: owner can log in, sees owner controls, and stays on or is routed to their own wishlist.
  • Browser QA share: clicking copy-link copies the exact direct URL and shows a localized success toast.

Manual QA Checklist

  • Root page with multiple users does not show a chooser/list/card grid of all wishlists.
  • Root page still works when no users exist: no broken empty directory copy.
  • Single-user deployments do not auto-redirect away from the new root page unless explicitly desired.
  • Opening a valid direct link loads the selected wishlist without requiring login.
  • Opening an invalid direct link has a clear not-found or fallback state; it should not silently show the hidden directory.
  • Share button remains available to guests and owners, including mobile widths.
  • Login modal is understandable in Russian, English, and Serbian.
  • SSO behavior remains coherent if SSO is enabled; root SSO should still end up on the authenticated user's wishlist.

Risks

  • Existing one-user redirect: loadUsers() currently redirects the root route to the only user. This must be changed or the new homepage will not appear on single-user installs.
  • Username discovery: owners need to remember their username. The login modal should not ask them for a share link.
  • API exposure: hiding the UI directory does not hide /api/users.
  • Clipboard permissions: clipboard writes can fail outside secure contexts or in older browsers; add a fallback and clear error toast.
  • Header density: theme, language, auth, settings, add, and share controls can crowd mobile headers; layout needs explicit mobile QA.

Rollback Plan

  • Revert the frontend component changes to restore the previous root-route user selection screen.
  • Keep direct wishlist links unchanged, so rolling back the root UI should not affect guest links.
  • If share-link copy causes issues, remove only the share button/handler without affecting wishlist browsing or reservation flows.
  • No database rollback is expected for the recommended frontend-only implementation.

Open Questions

  • Should /api/users also stop exposing the full user list publicly, or is hiding it from the homepage UI enough for now?
  • Resolved: root login should ask for username, not a share link. Direct links are copied from an opened wishlist for guests.
  • When an authenticated owner lands on the root page, should the app auto-open their own wishlist or show a "go to my wishlist" button?
  • Should the old "All wishlists" back button disappear from opened wishlist pages, since the root page will no longer be a directory?

Implementation Update

Approved and implemented on 2026-06-13. The root page no longer renders the public wishlist directory. It now shows a polished explanatory homepage for the invite-based wishlist service. Existing owners can log in from the primary CTA, new owners can open invite instructions, and guests continue to use direct wishlist links.

  • frontend/src/lib/UserSelect.svelte was renamed to frontend/src/lib/HomePage.svelte because the root route is no longer a user picker.
  • frontend/src/lib/HomePage.svelte now renders the festive explanatory root page without user cards, names, or slug list. It explains what Wishlist is, why it exists, how gift reservation works, and how owners/guests get access.
  • The hero now prioritizes Owner login visually, with Get an invite as a secondary action. The invite action opens a dedicated invite-instructions modal instead of performing an easy-to-miss scroll on small screens.
  • The homepage includes a product mockup with a guest link and distinct gift statuses: available, reserved, and purchased.
  • A lightweight footer was added to summarize the access model: owners sign in, guests open direct links.
  • frontend/src/App.svelte no longer auto-redirects single-user root visits, opens login from the root, navigates to the authenticated user's wishlist after login, and adds a copy-link button on opened wishlists.
  • frontend/src/lib/LoginModal.svelte now supports root login by username when no current wishlist slug is present.
  • frontend/src/lib/locales/ru.json, en.json, and sr.json were updated for the new root screen, username login field, invite modal, footer, mockup labels, and copy-link toasts.
  • frontend/tests/App.test.js and frontend/tests/setup.js were updated for the new root behavior, invite modal, and modal transition testing.
  • Dockerfile, docker-compose.dev.yml, and frontend/vite.config.js were adjusted so the dev compose runs the Vite dev server on localhost:5173 with bind-mounted source files, avoiding image rebuilds for frontend edits.

Known Limitation
